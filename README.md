## Learn More

### Contact bot protection

The contact form uses Vercel BotID Basic. `instrumentation-client.ts` protects
POST requests to `/contact` (the page invoking the Server Action), and
`next.config.ts` composes BotID rewrites with MDX configuration.
The contact action verifies BotID before accessing user data, writing messages
or sending email. Bot classification or verification failures reject submission
with a visible message; Upstash limits and the honeypot remain in place.
BotID is a security control independent of optional analytics consent.
No BotID secret is required. Deploy to Vercel to verify real bot classification;
local development intentionally returns `isBot: false` by default.
Health endpoints, cron jobs and other forms are not protected by this integration.

### Dependency health

The daily retention job at `/api/cron/contact-retention` sends a GET request to
`RETENTION_HEARTBEAT_URL` only after all database cleanup operations succeed,
including when there are no records to delete. Use the private HTTPS success/ping
URL generated by your monitoring provider, not `/api/health` or a status-page URL.
Set it in Doppler/Vercel; never expose it in client code or commit the real URL.
Configure the monitor for the `0 3 * * *` schedule (03:00 UTC) with a two-hour
grace period. Enable monitoring after deployment; no synthetic success ping is
sent during setup.

Heartbeat delivery has a five-second timeout and does not follow redirects.
Delivery errors are logged without the URL or response body and do not fail
completed cleanup. The cron response includes `heartbeat` with `sent`, `failed`,
or `not_configured`; missing configuration also produces a warning. Unauthorized
requests or failed cleanup never send a success heartbeat.

`GET /api/health` requires `Authorization: Bearer <HEALTH_CHECK_SECRET>`.
Configure a separate random secret (at least 32 characters) in your deployment
environment and monitoring service; do not place it in a URL or client-side code.
Responses are not cached. Unauthorized requests do not run dependency probes.

The endpoint runs these read-only checks in parallel, with a five-second deadline
per dependency: Postgres `SELECT 1` using the application's pooled Prisma client,
Redis Upstash `PING` (these are the same dependency), Neon Auth's anonymous
`get-session`, and Resend's domain-list API. No emails are sent, no user sessions
are forwarded, and provider responses, addresses and credentials are not returned.
Database transactions have their own timeout; a connection attempt may finish
after the endpoint's deadline because Prisma does not support AbortSignal here.

HTTP 200 means all probes passed; HTTP 503 means at least one dependency is
unavailable, not configured, or could not be fully checked. JSON includes
`status`, `checkedAt` and `checks` with each dependency's status and latency.
A Resend sending-only key may return `limited` / `permission_limited`: this is
not proof of a sending outage, but its permissions prevent this read-only check.
Do not broaden the application's key permissions just to make monitoring green.
These checks confirm the probed operations, not end-to-end login or email delivery.
Monitoring requests count toward provider quotas; avoid high-frequency polling.

### Privacy controls

Vercel Web Analytics and Speed Insights are mounted from the root layout only
when the current version of the `cookie-consent` cookie is `ACCEPT_OPTIONAL`.
Enable both products in the Vercel project dashboard before deployment.
Consent changes and clearing the preference reload the page to stop previously
loaded scripts. Both integrations strip query strings and fragments from event
URLs and drop events on auth, account, API and Terms acceptance routes.
Consent version 2 requires a new choice before enabling these measurements.

Account export at `/api/account/export` requires a signed-in session, but not
acceptance of the current Terms. A download link is available on `/terms/accept`.
The export scope is unchanged.

Upstash rate-limit identifiers use policy-specific HMAC-SHA-256 pseudonyms,
keyed with `INVOICE_DATA_ENCRYPTION_KEY` and a separate rate-limit domain prefix.
This key must be configured even for anonymous requests when Upstash is enabled.
Invalid or missing key configuration fails explicitly; raw identifiers are never
used as a fallback. Rotating the key resets rate-limit identities.
The `ratelimit:v2` namespace replaces the old raw-identifier namespace; old keys
are not reused and expire according to their existing TTL.

Application error logging uses fixed operation descriptions and allowlisted
Prisma error codes or HTTP status codes, without raw error messages, stacks,
request payloads or provider response bodies. Hosting and provider access logs
have their own settings and retention.

### Account deletion

Signed-in users can delete their account at `/auth/delete-account` without
accepting a new Terms version. The same form is available in account settings.
Identity is confirmed with a password or a sign-in email OTP sent to the
current account address (including passwordless accounts). Email OTP sign-in
and user deletion must be enabled in Neon Auth.

Application data is deleted transactionally before requesting identity deletion.
If identity deletion fails or requires an email confirmation, the form reports
that application data has already been removed. Terms acceptance evidence is
deleted in the same transaction, including unlinked entries matching the current
account email, unless explicitly retained for a concrete dispute. Contact messages
remain subject to their separate retention rules.

Before deleting an account involved in a concrete dispute, an authorized operator
can set `TermsAcceptance.retainedForDispute = true` on only the necessary records
and record an internal case reference in `disputeReference` (not the case contents).
These fields are not editable through user-facing forms. Review holds as part of
handling the case; do not use them for hypothetical future disputes.
Deletion marks retained records with `accountDeletionRequestedAt`. When retention
is no longer justified, set `retainedForDispute = false` and clear
`disputeReference`. The daily retention job deletes released records marked for
account deletion. Retained unlinked entries cannot be claimed by a new account
after an account deletion request.
